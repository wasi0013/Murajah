## 0. What's actually live today (read before building)

Verified against `source/sw.js`, `source/manifest.json`, `source/index.html`, and `app/public/_headers` — not assumptions:

- **Legacy SW** registers at `./sw.js` → `https://murajah.pages.dev/sw.js`, **scope `/`**. It controls every page on the origin right now.
- **Cache buckets**: `murajah-cache-v{VERSION}` (app shell + JS/CSS/JSON, network-first for navigations, stale-while-revalidate for the rest) and `murajah-fonts-v{VERSION}` (per-page QPC/Indopak/tajweed fonts, stale-while-revalidate with folder-aware matching). Both versioned by `CACHE_VERSION` (currently `26.05.31`); legacy's own `activate` already deletes old versions of *its own* buckets by prefix (`murajah-cache-`, `murajah-fonts-`).
- **`manifest.json`**: `scope: "./"`, `start_url: "./index.html"`. Home-screen icons on existing installs point at `/index.html` under scope `/`.
- **Navigation strategy is already network-first** (3s timeout, cache fallback) — the legacy authors already fought iOS Safari bugs once: the whole SW reads response bodies as `Blob` instead of `.clone()` specifically to dodge a WebKit "body is locked" tee bug. This is not our first iOS SW incident.
- **`EMERGENCY_RESET` message handler** deletes *every* cache key it finds (`caches.keys()` → delete all) and unregisters. It does **not** touch IndexedDB — Cache Storage and IndexedDB are separate origin-scoped APIs, and every cleanup routine we write, old or new, must preserve that separation.
- **`app/public/_headers`** (new app, already built in Phase 0) already sets `/index.html` to `Cache-Control: public, max-age=0, must-revalidate` and hashed `/assets/*` to `immutable`. This matters a lot for §3 below: the HTTP layer is *already* biased toward shell freshness independent of anything the SW does.
- **`app/package.json` has no `vite-plugin-pwa`** despite `redesign-2026.md` §2 claiming it's "already in the stack." It isn't. Task 10.1 adds it — correcting that stale claim rather than inheriting it.
- **No GA4/analytics wiring exists yet in `app/`** (legacy has `gtag.js`, measurement ID `G-JEMZ83QK37`). Without *some* signal, we cannot tell what fraction of real clients have handed off from the legacy SW to the new one during rollout — see 10.7.

### 0.1 Confirmed incident, 2026-07-23: this is not a hypothetical

While this phase was still in draft, a real iOS user hit **`WebKitBlobResource error 1`** / "Safari can't open the page" opening the Home Screen shortcut — a hard, unrecoverable-without-manual-cleanup navigation failure, not a staleness annoyance. Git history shows this is the **third** distinct WebKit navigation-caching bug this codebase has hit in succession: (1) `source/sw.js` originally crashed with "response served by the service worker has redirections" (fixed by stripping redirects, see the now-removed `PWA_STABILITY_AND_CACHE_PLAN.md`, April 2026); (2) that fix's `.clone()` usage then hit a "body is locked" tee bug, fixed by switching every navigation response to a `new Response(await res.blob(), init)` reconstruction (commit `29ff51da`, "ios cache issue fix"); (3) that Blob-reconstruction, applied to a **top-level navigation** Response and served to a Home Screen PWA that iOS aggressively backgrounds/kills/relaunches, is the most likely trigger of the current crash.

**Conclusion drawn from the pattern, not just this one incident:** iOS WebKit keeps finding a way to break on *any* synthesized/cached Response used to fulfil a navigation. Chasing the next clone/blob variant risks reintroducing a bug already fixed once (a clone-immediately-after-fetch fix was drafted and rejected for exactly this reason — see the retired draft in this file's history). **The fix that shipped as an immediate hotfix to the live `source/sw.js`** (2026-07-23, same day) is the one this phase now adopts as the target design for the new app too: iOS/iPadOS navigation requests bypass Cache Storage **entirely** — no `cache.put`, no `cache.match` fallback, nothing WebKit can later decide is stale or invalid. Android/desktop are untouched. Concretely:

- `source/index.html` detects iOS client-side (`isIOSDevice()`: UA sniff **or** `platform === 'MacIntel' && maxTouchPoints > 1` for the iPadOS-masquerades-as-Mac case) and registers `./sw.js?platform=ios` instead of `./sw.js`.
- `source/sw.js` reads `IS_IOS` from `self.location.search` once at top level; navigation requests branch to a new `networkOnlyNavigation()` (pure `fetch`, offline fallback only, zero Cache Storage) instead of the existing `networkFirst()` (left **byte-for-byte unchanged** for non-iOS). The install handler also skips precaching `NAVIGATION_SHELL_URLS` (`./`, `./index.html`, `./quiz.html`, `./privacy.html`) on iOS — those entries would be inert dead weight there (never read back) — and the `activate` handler's minimum-resource safety check excludes them on iOS too, so old-cache cleanup isn't permanently defeated.
- Font/data caching (`staleWhileRevalidate`, `staleWhileRevalidateFont`) is **identical on every platform** — this bug family is specific to navigation, not caching in general.
- Regression-tested in `tests/e2e/pwaIos.spec.js`: iOS registers `?platform=ios` and never caches the navigated document; non-iOS still registers the plain worker and still caches it exactly as before.

This supersedes the earlier draft of decision 2 below (which proposed "skip shell *precache* but keep NetworkFirst-with-cache-fallback" for iOS) — that was a real production incident, and the network-only version is the safer next iteration to build for the new app's SW, not a hypothetical to weigh in the open questions.

## 1. The core risk, stated plainly

Two failure modes, both unacceptable at this user count:

1. **Data loss** — any code path that clears storage overreaches and deletes IndexedDB (memorized pages, plans, streaks, recordings) instead of just the two named Cache Storage buckets.
2. **Stranded clients** — a device keeps its service worker serving the *old* `sw.js`/legacy shell indefinitely (iOS's unreliable background update-check is the concrete mechanism), so the user never even downloads the new app's teardown code, and appears "stuck" with no in-app way to recover (no address bar reload gesture in standalone PWA mode).

Everything below is organized around eliminating those two, in that priority order.

## Decisions (proposed — confirm before building)

1. **One SW source file, device-gated at *registration* time, not per-fetch inside the worker.** Detecting iOS inside the SW is strictly worse than in the page — `navigator.maxTouchPoints`/`navigator.platform` aren't reliably available in the SW global scope the way they are on `window`, and iPadOS (13+) reports as desktop Safari (`platform: "MacIntel"`) so a naive `/iPad|iPhone/.test(userAgent)` check misses iPads entirely. Boot code (`app/src/main.ts`) decides device class once, then registers `/sw.js?platform=ios` vs `/sw.js` (plain). Use `vite-plugin-pwa`'s **`injectManifest`** strategy (a hand-written SW source we control), not `generateSW`, so the SW can branch once at top level on `self.location.search` to decide whether to call `precacheAndRoute(self.__WB_MANIFEST)` at all. A query-string difference is a legitimate distinct registration in the SW spec — no hidden per-request branching, no dual build output to maintain.
2. **The iOS fix is "navigation never touches Cache Storage," confirmed by a real incident, not a hypothetical.** Originally drafted as "never precache the shell, but keep NetworkFirst-with-cache-fallback for navigation" — reasoning: Workbox `precacheAndRoute` would serve `index.html` cache-first, and iOS's SW update-check is unreliable enough that a stale precached shell can sit for a long time with no visible way to force a refresh. That reasoning undersold the risk. §0.1 documents a confirmed production crash (`WebKitBlobResource error 1`, "Safari can't open the page," unrecoverable without manually clearing site data) — the third distinct WebKit navigation-caching bug this codebase has hit — and the hotfix that shipped the same day to `source/sw.js`: iOS navigation is **network-only**, full stop — no `cache.put`, no `cache.match` fallback, nothing synthesized ever reaches WebKit for a top-level navigation. `_headers` already forces `index.html` to revalidate every load, so the HTTP layer (not the SW) is the freshness mechanism now regardless of platform. **Runtime caching for per-page Quran data + fonts is unchanged on iOS** (stale-while-revalidate, same as everywhere else) — those are inert data files, not app code or navigations, and are not implicated in any of the three incidents. This preserves most of the offline reading value on iOS while removing the SW from the navigation path entirely on the one platform where it keeps finding new ways to break. See the open question below for the more extreme alternative (no SW registered on iOS at all) and why it's still not the recommendation.
3. **Legacy teardown is universal, not iOS-specific.** Every platform currently has the legacy SW controlling `/`. New-app boot, on every platform, must detect and retire it before registering the new one — this is the thing that actually protects the 1000 existing users, and it's orthogonal to the iOS precaching decision.
4. **Cache cleanup is prefix-matched against the two known legacy names, never a blanket `caches.keys()` wipe.** `EMERGENCY_RESET`-style "delete everything" is a manual last-resort the *user* can still trigger from a future settings/support surface if we choose to keep it, but automatic teardown code must only ever target `murajah-cache-` / `murajah-fonts-` prefixes so it can never eat the new app's own precache/runtime-cache buckets (which Workbox names differently, e.g. `workbox-precache-v2-...`).
5. **A forced-refresh prompt on activation, not a silent reload.** Legacy already does `SW_UPDATED` postMessage → the page reacts. Given this update coincides with a full UI framework swap (vanilla/Vue-CDN monolith → new Vite SPA), a currently-open tab cannot hot-swap — but silently yanking the page out from under someone mid-recitation is worse than the bug we're fixing. Show a small "Murajah has a big update — tap to refresh" toast (non-blocking, dismissible, re-offered next visit) rather than auto-reloading. Exception: the very first legacy→new handoff (10.7) may warrant a one-time stronger nudge — decide during build once 10.4's toast exists to compare against.

## 10.2 — Legacy service-worker teardown (universal — the load-bearing task) ✅ IMPLEMENTED

- [x] **10.2.1** `unregisterLegacyServiceWorkers()` (`app/src/core/pwa/legacyTeardown.ts`) unregisters every registration whose active/waiting/installing script's **pathname** isn't `/service-worker.js` — **narrower than the original "any registration at all" sketch, and this narrowing is load-bearing.** Teardown runs on *every* boot (not just the first), so "any registration" would unregister the new app's own still-active registration on every routine visit — confirmed in testing as a real self-inflicted reload loop (every boot "tore down" the registration the previous boot had just created). - [x] **10.2.3** Sequencing confirmed: teardown → register → (device-appropriate) activation → normal app boot proceeds independently (IndexedDB/Phase-1 migration has no dependency on SW state).
- [x] **10.2.4** Regression guard present in the unit suite (`pwa-legacy-teardown.test.ts`): asserts the cache-deletion call is prefix-scoped and would not be affected by an `EMERGENCY_RESET`-style blanket wipe — that code path was never ported.

## 10.4 — Update-detection & refresh UX ✅ IMPLEMENTED (redesigned from the original sketch)

- [x] **10.4.1** Implemented as `usePwaUpdate()` (`app/src/composables/usePwaUpdate.ts`) — **not** a wrapper around `vite-plugin-pwa`'s `registerSW()` virtual module, since that helper can't express the device-gated registration URL (10.1.3) or the teardown-must-run-first ordering (10.2). It's a hand-rolled `PwaController` (`registerServiceWorker.ts`) instead, exposing `onNeedRefresh`/`onControllerChange`/`applyUpdate`/`checkForUpdate`. The toast is decision 5's non-blocking "Update available — tap to refresh" (`duration: 0`, re-offered every boot until acted on since nothing persists dismissal — acceptable, matches "re-offered next visit").
  - **A real reload loop was found and fixed during implementation**, not merely anticipated: an unconditional `window.location.reload()` on every `controllerchange` — including a fresh/first-ever client's own `clientsClaim()` acquiring an uncontrolled document — chained into a genuine repeated-install cycle when tested against a still-active prior worker (the exact legacy-handoff shape). Fixed with an `applyUpdateCalled` guard in `registerServiceWorker.ts`: only a reload the app itself triggered (via `applyUpdate()`, i.e. an explicit user tap or the first-handoff nudge) ever reloads the page — a first/fresh activation with no prior controller does not, which is also just the correct general PWA pattern (reloading on first install is a well-known footgun). Regression-tested in `pwa.spec.ts`: three post-migration boots must produce exactly one load each and never show the update toast.
  - **Open question 2 (approved: stronger first-handoff nudge)** is implemented via `onNeedRefresh`'s `isFirstHandoff` parameter: the just-migrated case shows `"Murajah has been rebuilt — refreshing now…"` for 1.5s then calls `applyUpdate()` automatically, instead of waiting for a tap.
- [x] **10.4.2** `visibilitychange`/`focus` → throttled `checkForUpdate()` (`registration.update()`), 60s window. **One correction found in testing:** the throttle's clock must start at `init()` time (module load), not at zero — a flicker firing in the same instant as boot must not immediately re-check, since that raced a manual `update()` against the registration's own still-settling initial install and was part of what produced the reload-loop symptom above.
  - *Verified:* `tests/unit/use-pwa-update.test.ts`.

## 10.5 — Offline download manager UI *(carried over from the old 9.6.2, unchanged in intent)* ✅ IMPLEMENTED

- [x] **10.5.1** Implemented as `useOfflineDownload()` (`app/src/composables/useOfflineDownload.ts`) + a "Offline reading" section in Settings — two independent, opt-in packs rather than one combined "optimized page data/fonts" pack, per a scoping call made during build:
  - **Text pack** (~8 MB, on by default UI-wise — i.e. offered first): drives `DataClient.getPage('qpc', n)` across all 604 pages into the existing `murajah-assets` AssetCache (Phase 1 plumbing, reused as-is).
  - **Images pack** (~68 MB, separate opt-in, size shown, matching §4.1): drives `MushafClient.getPageBlob(n)` into `murajah-images` (96MB cap — comfortably holds the full ~68MB scan set with no eviction risk, confirmed by reading `imageTransport.ts`).
  - **Fonts deliberately excluded from the pack**, unlike the original sketch: `FontLoader` has no persistent (IndexedDB/Cache Storage) cache of its own today — only a 12-face in-memory LRU — so "downloading" fonts would need new caching infrastructure. Per-page fonts already cache themselves via the SW's `/fonts/*` stale-while-revalidate route (§10.1) as the reader organically visits pages; bulk-downloading the full ~145MB font set as a "default pack" would also be a poor product default even if the infra existed. Noted as a real scope cut, not an oversight.
  - **Resumable "for free":** each `getPage`/`getPageBlob` call is itself cache-first, so restarting the pool after a cancel or a reload just fast-skips already-downloaded pages rather than re-fetching — no separate progress-index persistence needed. A `getPref`/`setPref` flag per pack (`offlineTextDownloaded`/`offlineImagesDownloaded`) short-circuits full re-verification on a later visit once complete.
  - **Cancelable:** a "Cancel" action during download; canceling leaves a "tap to resume" state (re-running the pool from the top, same fast-skip behavior).
  - *Verified:* unit (`tests/unit/offline-download.test.ts`, mocked clients — full-download completion, cancel-mid-flight-then-resume, pack independence, hydrate-from-a-prior-session) and e2e (`tests/e2e/offline-download.spec.ts`, real clients against a real preview build — progress advances, cancel offers resume, and a spot-check confirms pages are genuinely persisted in `murajah-assets`, not just counted in UI state; doesn't wait out a full 604-page download, that's not what's under test). Network-off readability and the 10.3 iOS caveat follow from the underlying caches (already covered by their own existing tests) rather than being independently re-verified here.

### 10.7.4 rollback dry-run (written analysis; a live Cloudflare Pages revert was not executed — no production deploy exists yet to roll back from)

**Scenario:** Phase 11 ships the new app to production, some fraction of clients migrate (teardown runs, legacy SW/caches gone), then a defect is found and the production deploy is reverted to the last legacy build.

**Claim: this is safe with respect to user data.** Walking it through:

1. **Already-migrated clients** (10.2 ran): their legacy SW registration and `murajah-cache-*`/`murajah-fonts-*` buckets are gone — by design, that's disposable Cache Storage, not data. `murajah-db` (IndexedDB) was never referenced by any teardown code path (10.2.2, structurally enforced — no `indexedDB` symbol anywhere in `legacyTeardown.ts`). Reverting the deploy re-serves the **old** `index.html`/`sw.js`, which the browser's own `Cache-Control: no-cache` on `index.html` (both codebases set this) fetches fresh on next navigation. The re-served legacy `sw.js` re-registers itself and resumes reading/writing `murajah-db` exactly as it did before the migration ever started — it never stopped being able to, since nothing about the new app's teardown touched its schema.
2. **Not-yet-migrated clients**: unaffected either way — they never ran 10.2, so a rollback is a no-op for them (same old app, same old SW, same `murajah-db`).
3. **Forward-compatibility check (the one real risk to confirm, not assume):** does the *new* app ever write to `murajah-db`, or to a differently-versioned/differently-shaped store the legacy app's code wouldn't understand after a rollback? **No** — confirmed by reading `app/src/core/storage/*`: the new app's user-data persistence lives in its own, separate IndexedDB database (`murajah-userdata`, versioned independently — see `userData.ts`), never `murajah-db`. The only *reads* from legacy data are the manual export/import bridge (`legacyExport.ts`, a JSON file the user explicitly exports/imports — not a live migration touching `murajah-db` on boot) and the Phase-5 plans/streak migration noted in `legacy-schema.md` §1 as "handled directly from IndexedDB when the plans feature lands" — that migration path reads `murajah-db`'s `plans`/`planHistory` stores but this phase's rehearsal (10.7.3) already proves those specific stores survive a teardown boot byte-identical, so a subsequent rollback finds them exactly as legacy left them.
4. **Net:** a rollback after some clients have migrated is safe — no client's data is lost or corrupted by the round trip, in either direction. What rollback does **not** undo is the *UX* of having briefly run the new app (already-migrated clients revert to seeing the old UI again) — an acceptable, expected consequence of a rollback, not a data-safety concern.

**Not dry-run because not yet applicable:** the actual Cloudflare Pages "revert to prior deployment" mechanic itself (dashboard action or `wrangler pages deployment` rollback) has not been exercised, because Phase 11 hasn't shipped anything to production yet to roll back from.
