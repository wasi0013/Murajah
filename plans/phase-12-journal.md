# Phase 12 — Practice Journal

**Parent:** [redesign-2026.md](./redesign-2026.md) §5 (new phase — Phase 8 explicitly dropped "notes/journal" on 2026-07-18; reinstated here, considerably more capable than a bare note field, per product-owner request 2026-08-23). **Prereqs:** Phase 4 (`progress` store: `memorized`/`strength`/`reviewData`), Phase 5 (`dayLog` store + `DayRecord`, `useStreak`, `streaks.ts`), Phase 7.6 (`recordings` store), Phase 9.2 (`ProgressView`'s segmented-tab pattern, `strengthBands.ts`). **Goal:** an automatic daily journal — a calendar of what was actually done each day (memorization, revision, weak-page work, listening/recording activity, memorization-strength band changes) — plus an optional short reflection note per day, at zero migration risk to the ~1000+ users already running on live IndexedDB.

> Status: **BUILT** — all tasks 12.1–12.8 implemented and merged on `feature/journal-phase-12` (2026-08-23). Full suite green (unit + e2e) at every step; see each task's commit for its own test coverage. Not yet reviewed or shipped to production.

## Why this is a storage-design problem first, a UI problem second

The screenshot's UI (calendar → tap a day → see logged sections + a note) is the easy 20%. The hard 80% is that most of what the day view shows **already exists** somewhere in the app, and duplicating it into a new journal-entry blob would both bloat storage and create a second source of truth that drifts from the first. So the core design question this phase answers is: **what is genuinely new state that must be persisted, versus what is computed on demand from stores that already exist?**

Answer: only two things are new state — the **reflection note** (free text; nothing else produces it) and the **strength-band-change event** (e.g. a page crossing from Ḍaʿīf → Mutawassiṭ is a moment in time; `progress.strength` only holds the *current* value, so the transition is unrecoverable once overwritten unless captured when it happens). Everything else in the mockup — reading/revision/weak-page completions, recordings, habit completions — already has a durable, date-addressable home (`dayLog.byDate`, `recordings.items` keyed by `recordedAt`) and is read, not written, by this feature.

## Decisions (confirmed 2026-08-23)

1. **Nav placement:** Journal is a 4th segment on the existing `/progress` route — `Overview | Juz | Pages | Journal` — not a new primary tab and not buried in "More". Reuses `SegmentedControl` exactly as Phase 9.2 wired Juz/Pages in `ProgressView.vue:41`. Zero bottom-tab-bar changes, zero new route-level bundle budget category (it rides `ProgressView`'s existing lazy chunk, though see 12.7 for why it still needs its own size-limit line once it stops being trivially small).
2. **`HistorySheet.vue` is retired.** Its job (streak numbers + a 90-day completed/partial/none heatmap) is a strict subset of the Journal calendar. Today's entry point that currently opens the sheet instead routes to `/progress` with the Journal segment pre-selected. `useStreak`/`buildHistory`/`streaks.ts` are **not** removed — the streak numbers move to the Journal panel's header and `buildHistory`'s day-state logic is reused for calendar-cell coloring (see 12.4). Deleted only after 12.4's e2e coverage is green (12.8).
3. **Per-day time tracking is deferred**, not built here. `progress.readingSeconds`/`listeningSeconds` (`userData.ts:92-93`) are lifetime cumulative counters with no daily breakdown, and today's app never writes them per-day. Adding that is a new continuous-write path (ticks every active second) with its own performance design and belongs in a follow-up phase, not folded into this one. The Journal day view ships **without** a "Time Logged" row in v1; the row is left out entirely rather than shown as a fake or misleading estimate.
4. **A reflection note is editable for any past day, indefinitely**, not just today. This is what makes the merge rule for imported backups a real design problem (§ Merge semantics below) rather than a "today only" special case — a user could plausibly edit yesterday's note on two devices before syncing via backup.

## Data model

### New: per-date journal entry (`stores/journal.ts` + `core/storage/userData.ts`)

```ts
export interface JournalEvent {
  /** Stable id — `${type}:${page}:${createdAt}` — so imports can dedupe by identity, not by array position. */
  id: string
  type: 'band-up' | 'band-down' | 'bulk-memorized'
  page?: number                 // absent for 'bulk-memorized' (aggregate, see 12.2)
  fromRank?: StrengthRank
  toRank?: StrengthRank
  count?: number                // 'bulk-memorized' only — how many pages
  createdAt: string             // ISO instant, for sort + dedupe tie-break
}

export interface JournalEntry {
  date: string                  // YYYY-MM-DD, local calendar day — matches DayRecord.date
  note: string                  // '' = no note; capped at NOTE_MAX_LEN (280, tweet-sized per the brief)
  noteUpdatedAt: string | null  // ISO instant of the note's last edit — the merge tie-breaker
  events: JournalEvent[]        // capped at MAX_EVENTS_PER_DAY (see 12.2); overflow tracked, not silently dropped
  eventsOverflow: number        // count of events beyond the cap, for an honest "+N more" instead of silent loss
}
```

### Storage: per-date keys in the existing `data` object store — no `DB_VERSION` bump

`userData.ts` keeps every store's data behind a **single key** (`PROGRESS_KEY`, `DAYLOG_KEY`, …), each holding one whole-blob JSON value, persisted via a debounced `watch(() => store.snapshot(), …, { deep: true })` (see `useDayLogPersistence.ts:18-25`). That pattern is correct for `dayLog` (bounded — one flag + a handful of page numbers per day) but is the wrong shape here: a note-editing keystroke would deep-clone and rewrite **the entire journal history** on every debounce tick, a write cost that grows without bound as a user's history grows. This is the feature's single biggest performance trap and the reason this isn't "just add a `journal` key like everything else."

Instead, journal entries are individually keyed inside the **same** `data` object store `userData.ts` already opens (`DB_NAME='murajah-userdata'`, `STORE='data'`) — no new object store, no `DB_VERSION` bump, no `upgradeneeded` migration:

- Key scheme: `` `journal:${date}` `` (e.g. `journal:2026-08-23`), value = a plain `JournalEntry`.
- Range read for a visible month: `store.getAll(IDBKeyRange.bound('journal:2026-08-01', 'journal:2026-08-31'))` — both bounds are exact known dates (no sentinel needed here, unlike the "every date ever" scan below), cheap, sorted-by-key-for-free since `YYYY-MM-DD` sorts lexicographically. `idb.ts` already has `idbGetAll` for exactly this shape (`idb.ts:35-36`); it just needs a range-capable overload (`IDBObjectStore.getAll(query)` already accepts an `IDBKeyRange`, so this is a signature widening, not new IDB surface).
- A day's write touches **one key**, independent of history length — O(1) per edit, not O(days).
- No two-tab "blocked upgrade" hazard: `idb.ts:openDb`'s `indexedDB.open(name, version)` only blocks on a **version** change; since this ships without bumping `DB_VERSION`, every existing open connection (including one held in another tab) keeps working unmodified. (Flagging this explicitly because `openDb` has no `onblocked`/`db.onversionchange` handling at all today, and `userData.ts` shares one `dbPromise` across every key — a version bump *would* be a real multi-tab hazard for this app specifically. Avoiding one is a feature of this design, not an accident.)
- `hasAnyUserData()` (`userData.ts:688-696`, gates the onboarding modal via `stores/onboarding.ts`) does a bare `count()` over the whole store — new `journal:*` keys are indistinguishable from any other key to it, but that's harmless here: a journal entry is only ever created as a byproduct of using the plan/reader/recorder, all of which already write other keys first, so a "fresh install with only journal data" is not a reachable state. No change needed, but worth the one-line note so a future reader doesn't have to re-derive it.

### Retention caps (unbounded growth is the other perf trap)

- `MAX_EVENTS_PER_DAY = 20`. Past it, a new event evicts the **oldest** event and counts the eviction in `eventsOverflow` — a heavy single day (e.g. a bulk-mark session touching dozens of bands) keeps its most recent activity visible and gets one honest row ("+12 more changes") rather than an unbounded array or, worse, going stale on its earliest 20 events while silently dropping everything after. This keeps-most-recent policy is shared verbatim by `applyJournalEvent` (live) and `mergeJournal`'s re-cap (import) — an earlier draft had them disagree (live FIFO-froze at the cap; merge evicted oldest), caught in review.
- Notes are **never** capped by age or count — one note per calendar day, and a day already exists in the key space or it doesn't; there's no separate "note history" to prune.
- No cross-day pruning in v1 (e.g. "delete journal entries older than 2 years"). Flag as a candidate for a future settings-driven retention control if IndexedDB size ever becomes a support complaint — not a concern at the data volumes one person's daily practice produces (a few hundred bytes/day even at the cap).

  - **Deviation from the original wording, decided during implementation:** rather than one generic `saveJournalEntry(entry)`, shipped as two narrow functions — `saveJournalNote(date, note, noteUpdatedAt)` and `appendJournalEvent(date, event)` — each its own read-modify-write transaction touching *only* the fields it owns (note fields; events/`eventsOverflow`, respectively). This is what makes 12.1.4's guarantee ("never clobber a field the caller didn't touch") hold **by construction** rather than by a generic object-spread merge trying to infer which fields of a full `JournalEntry` were actually intended as changes — a `{...existing, ...entry}` merge can't tell an intentionally-cleared note from a fabricated blank one from a `ensure()`'d-but-never-loaded entry, since both look identical (`note: ''`). Two purpose-built functions have no such ambiguity: `saveJournalNote` never even receives an `events` array to accidentally overwrite, and vice versa. This also directly resolves 12.1.4's blocker (a windowed store calling `appendJournalEvent` for a date it never loaded from disk cannot clobber that date's note, because the function was never given a note to write) — so 12.1.4 shipped as part of this same slice rather than as a follow-up patch; there was no correct intermediate state where 12.1.1 existed without it. **Downstream tasks (12.1.2/12.1.3/12.2.x/12.6.x below) should call `saveJournalNote`/`appendJournalEvent`/`saveFullJournal`, not a `saveJournalEntry` that doesn't exist.**

## 12.6 — Backup export/import (the merge behavior this feature specifically requires)

This is the one place this feature's persistence semantics **deliberately differ** from every existing key in `exportImport.ts`, and that asymmetry must stay documented in the code, not just in this plan — a future maintainer reading `importUserData` should not have to guess why `journal` doesn't follow the "just overwrite" pattern every other key uses.

- [x] **12.6.1** Add `journal?: StoredJournal` (`Record<string, JournalEntry>`, matching the `StoredDayLog` shape) to `ExportSnapshot`, wired into `buildExport`/`sanitizeSnapshot` exactly like every other optional key (`exportImport.ts:87-100`, `:164-179`). `exportUserData` gathers it via `loadFullJournal()` (12.1.1) — one `IDBKeyRange.bound('journal:', 'journal:~')` scan (`~` is the prefix-scan upper bound — see `journalStorage.ts`'s doc comment on `JOURNAL_RANGE_ALL` for why it replaced an earlier Unicode-noncharacter sentinel), bounded by however many distinct calendar days the user has ever practiced on, which is what makes it safe to scan in full (the per-day event cap from the Data model bounds each *entry's* size, not the count of entries scanned here — worth stating precisely since those are two different bounds).
- [x] **12.6.2** `mergeJournal(current: JournalLog, incoming: JournalLog): JournalLog` in `core/storage/userData.ts` (pure, unit-testable, no IDB dependency — same style as `backfillReviewDates`): union by date key.
  - A date present in only one side passes through unchanged.
  - A date present in **both**: `note` — the side with the later `noteUpdatedAt` wins (an empty incoming note with no `noteUpdatedAt` never clobbers an existing note — only a genuinely newer edit does). `events` — union by `id`, de-duplicated, re-sorted by `createdAt`, then re-capped at `MAX_EVENTS_PER_DAY` keeping the most recent; `eventsOverflow` is the **larger** of the two sides' counts plus any new overflow from re-capping — **not** the sum (caught in review: summing isn't idempotent, since a repeat import of the identical backup would keep adding the same already-counted loss to itself).
  - *Verify:* unit (the highest-value tests in this whole phase — this is the one function actually protecting 1000+ users' local data across an import) — disjoint dates union cleanly; same-date same-note (idempotent import) produces no change; same-date, incoming has a strictly later `noteUpdatedAt` → incoming note wins; same-date, current is later → current note wins (import must not regress a newer local edit); overlapping events with shared ids dedupe to one; a backup **without** a `journal` key at all leaves the live journal completely untouched (the "no journal in backup → keep current, start fresh only if current is *also* empty" case from the brief — "fresh" here just falls out of "untouched empty stays empty"); re-merging the same overflowing backup two and three times leaves `eventsOverflow` stable, not growing.
- [x] **12.6.3** Wire into `importUserData` (`exportImport.ts:215-239`): `if (snap.journal) { const merged = mergeJournal(await loadFullJournal(), deserializeJournal(snap.journal)); jobs.push(saveFullJournal(merged)) }` — `saveFullJournal` (12.1.1) writes the merged result in one transaction, not one `saveJournalEntry` call per date. Add a code comment at this exact call site cross-referencing this doc/decision, so the contrast with `dayLog`'s `saveDayLog(deserializeDayLog(snap.dayLog))` two lines above (replace, not merge) reads as intentional rather than an inconsistency to "fix" later.
  - *Verify:* e2e — import a fixture backup containing journal entries into a profile that already has different-dated live journal entries; after import + reload, both sets of entries are present, confirming end-to-end merge (not just the pure-function unit level).
- [x] **12.6.4** Legacy (v2.0.0) backups never carried journal data — `fromLegacy` (`exportImport.ts:106-131`) needs no change; `readImport`'s legacy branch simply never populates `snap.journal`, which 12.6.3's `if (snap.journal)` guard already handles as a no-op merge.

## Performance risk register (critical evaluation, summarized)

| Risk | Where it would bite | Mitigation in this plan |
|---|---|---|
| Whole-history rewrite per keystroke | Note autosave, if journal followed `dayLog`'s deep-watch-whole-blob pattern | Per-date IDB keys (§ Data model); per-entry debounce (12.1.3), not a deep watch of the full map |
| **Silent note/event loss from the windowed store** | An event fires (from any route) for a date not currently loaded into the Journal panel's in-memory store; a naive save blind-overwrites whatever was already on disk for that date | `saveJournalNote`/`appendJournalEvent` are each read-modify-write inside one transaction and each own only their own fields, never a blind `put` of a whole entry (12.1.1/12.1.4, shipped) — the correctness guarantee lives in the storage layer, not in callers knowing whether a date happens to be resident |
| Event storm from one bulk action | `bulkMarkMemorized` over hundreds of pages | Coalesced into one aggregate event (12.2.2), not one per page |
| Unbounded per-day growth | Years of repeated mistakes/reviews on volatile pages | `MAX_EVENTS_PER_DAY` cap + honest overflow count (12.2.3, Data model) |
| Full recording-blob hydration in a read path that runs on every day-expand | `loadRecordings()` pulls every `ArrayBuffer` | Filter the already-hydrated `recordings` store in memory; never re-load (12.3.3) |
| Heavyweight computation in the calendar grid | `calculateAllWeaknesses` (604-page loop) or similar run for all 31 visible cells | Calendar cells use only cheap boolean/count flags (12.3.1); full detail computed lazily on tap only (12.3.2) |
| Multi-tab IndexedDB blocked upgrade | Any `DB_VERSION` bump against `userData.ts`'s single shared `dbPromise` with no `onblocked` handling | Avoided entirely — new data lives in the existing object store under new keys, no version bump (§ Data model) |
| Silent data loss on backup import | A naive "journal always replaces" import wiping a newer local edit | Dedicated `mergeJournal`, last-write-wins by `noteUpdatedAt`, event union by id (12.6.2), with the asymmetry vs. `dayLog`'s replace semantics explicitly documented in code |
| Bundle bloat on the already-budgeted `/progress` route | New calendar + sheet components landing in `ProgressView`'s chunk unbudgeted | New/updated `size-limit.json` entry (12.7.3) |

## Explicitly out of scope for this phase

- Per-day time-logged tracking (Decision 3) — candidate for its own follow-up phase with its own write-path design.
- Cross-device live sync — this app is local-first with manual JSON backup/import as the only transfer mechanism; that doesn't change here.
- Retention/pruning UI for very old journal history — not a real problem at the data volumes involved (Data model, Retention caps); revisit only if it becomes one.
